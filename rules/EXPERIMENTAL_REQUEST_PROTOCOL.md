# Experimental / Exploratory Request Protocol v42

This protocol applies when the user asks for broad creative work such as:

- experimental builds
- unique features
- creative applications
- futuristic or stylized studies
- vague prompts intended to explore possibilities
- "see what you can do" or "try new ideas"

## Core rule

```text
Vague experimental prompt = exploration mode, not consolidation mode.
```

Do not default to known-safe motifs just because they worked in earlier studies. Past discoveries are **technical guardrails**, not automatic design templates.

## Required design behavior

Before scripting, create a divergent concept plan. Each proposed build should differ by at least two of the following:

- macro silhouette
- part family
- structural logic
- effect strategy
- architectural purpose
- risk level
- view angle / intended use
- skyline, interior, facade, roof, floor, or environmental role

## Required mix for 10-build studies

A 10-build experimental file should usually include:

| Type | Minimum target |
|---|---:|
| safe / likely buildable | 2 |
| refined known idea | 1-2 |
| wildcards using underused part families | 3-4 |
| effect-driven variants | 1-2 |
| structural / usable modules | 2 |
| sculptural / skyline identity pieces | 1-2 |

Do not create ten mild variants of the same idea unless the user specifically asks for a density/scale/orientation study.

## Comfort-zone suppression

The following motifs are allowed only when they have a clear reason. They must not become defaults:

- short-wall / trim rings
- red `B_SHL_E` lens bands
- antenna crowns
- light-fissure beacons
- Aeron blade cones
- stacked room crowns
- circular signal rings
- square test pads
- repeated "robot arm around a thing" arrangements

If a known motif is used, the script comment or manifest must state what is new about its use.

## Purposeful part rule

Every part family in an experimental script must have a visible role:

- structure
- socket / adapter
- visible lens or emitter
- hidden FX emitter
- gantry / rail / connector
- paneling / facade
- docking interface
- silhouette maker
- scale cue
- lighting/color cue

Delete or replace parts that exist only because they "make it look finished."

## Study quality standard

Experimental builds should read as advanced glitch-building studies:

- strong macro silhouette first
- connected visible structure
- density in focal zones
- parts grounded or mounted
- intentional color zones
- visible part-family logic
- no floating antennas unless float is the designed effect and structurally framed
- no sparse concept thumbnails

## Variant retention rule

Screenshots and in-game review override code intent.

- If the user screenshots or praises a variant, analyze and preserve the lesson.
- If a variant is not screenshotted, not discussed, and not clearly promising, treat it as a removal candidate.
- Do not keep weak variants just to satisfy a requested count.
- When a design fails, record why it failed and whether the failure is visual, geometric, part-choice, orientation, density, or project-fit.

## Script output requirement

Substantial experimental generators should include a `BUILD OBJECT USE MANIFEST` in comments or printed output with:

- ObjectID
- part family
- role in the build
- use type: structure / detail / FX / connector / lens / data / silhouette
- orientation notes
- scale range
- reason for selection
- known rule/fix checked
- experimental risk level

## Exploration checklist

Before delivering a script, verify:

```text
EXPLORATION MODE CHECK
Prompt classified as experimental/exploratory when appropriate: PASS
Divergent silhouettes planned: PASS
Underused part families considered: PASS
Comfort motifs suppressed unless justified: PASS
Every part has a visible role: PASS
No filler rings / filler antenna crowns / filler pads: PASS
Non-screenshotted weak variants not carried forward: PASS
Study/core separation preserved: PASS
```
