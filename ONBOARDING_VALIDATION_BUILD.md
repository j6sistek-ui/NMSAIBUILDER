# ONBOARDING VALIDATION BUILD — Builder-Readiness Gauntlet

Purpose:
Bring a new chat to **Builder Readiness**, not just Source Readiness. Reading the package (the ONBOARDING CHECKLIST: READ/SKIPPED) proves you have the documents in context. It does **not** prove you can build correctly. This gauntlet does — by forcing one real, intentionally minimal build through the full process, including failure handling, before the first user build request.

Source Readiness (checklist) is necessary but NOT sufficient. Builder Readiness requires passing this gauntlet.

## The gauntlet is a real micro-build, not a simulation

Validation build (intentionally minimal, so it is quick):
- Simple floor
- Simple wall
- Simple roof (one connected shell — not three loose parts)
- One `S_RAMP` (or any part listed in `library/part_placement_maps/part_placement_map_index.json`)

**Why the ramp is required, not optional:** the validated-logic-reuse gate is auto-required for every build-type request and **FAILS** a build that uses zero parts from the placement-map proof ledger ("no known ObjectIDs detected"). Floor/wall/roof are not in that ledger; only the ramp/trifloor/billboard families are. Without at least one ledger part, this onboarding build dead-ends on a gate it cannot satisfy. Including one `S_RAMP` both clears the gate and makes the gauntlet actually exercise validated-logic reuse — which is the point of that gate.

It must produce the same artifacts any real build owes:
- placement authority summary
- build packet (generated by `validation/part_context_resolver.py`)
- build sheet, with `applicable_rule_behaviors` and a `build_application` per part
- `run_gate` result — **actually run** `validation/run_gate.py` on the micro-build script and paste its output. Never a hand-typed PASS.
- `BUILD COMPLIANCE MANIFEST` summary (gate-verified via `validation/compliance_manifest_check.py`).

## Pass condition is the gauntlet, not "package read"

Run these stages in order and record each:

1. **Generate build artifacts** (packet + build sheet + script).
2. **First gate:** run `run_gate.py`. Paste the verdict.
3. **If the first gate FAILS:** do not stop and do not hand-wave.
   - **Diagnose** the root cause (which check, why).
   - **Correct** the script/packet.
   - **Second gate:** re-run `run_gate.py` and paste the new verdict.
4. **Builder-readiness verdict:** emit an explicit line:
   `BUILDER READINESS: READY` (only if a `run_gate` PASS is recorded) or `BUILDER READINESS: BLOCKED (<reason>)`.

If the first gate passes cleanly, still state that no correction was needed and emit the verdict.

Only after `BUILDER READINESS: READY` is recorded may the AI request the user's build objective.

## Why the failure loop is mandatory

A gauntlet that can only be passed by a clean first run does not prove the AI can *recover* from a real failure — which is most of real building. The diagnose -> correct -> second-gate loop is the part that proves Builder Readiness. A new chat that never sees a failure has not been tested.
